# 05 — Relation specification and public-input construct (V2-C1, frozen)

Sources: `circuits/src/*.circom`, generated by `circuits/gen.py` (derived from the P0 generator; the Merkle,
selector and credential-hash templates are byte-for-byte the V1 ones). Hashes, constraint counts and key hashes:
`circuits/CIRCUITS.csv`. Setup script: `circuits/build_all.sh`.

## 1. Base relation (k = 1, `c1_k01`)

R_V1,d with d = 11: the prover knows a credential record (nameHash, majorCode, studentId, issueDate), its leaf
leaf = Poseidon₄(record), and a Merkle path (pathIndices[11], siblings[11]) such that the Poseidon₂ path from leaf
reaches `root`. **Public:** root (k = 1). This is exactly the V1 relation; its R1CS is byte-identical to the P0 `v1_d11`
R1CS (sha256 `670ffb5d…0b07`), and its deterministic PLONK key is byte-identical to the P0 / V1 key
(sha256 `55b85a8c…`). Holder binding, nullifiers and predicates are outside this relation (as in V1).

## 2. Context-tag family (`c1_ctx_kKK`, k ∈ {2, 4, 6, 8, 12, 16, 24, 32}; 64 as limit check)

R_ctx,k = R_V1,11 ∧ ⋀_{i=0}^{k−2} ( tagSq_i = tag_i · tag_i ), with **public** [root, tag_0 … tag_{k−2}].

What the added constraint means, exactly:

- Each tag is one field element of BN254's scalar field, supplied by the verifier's caller as a public input.
- The constraint tagSq_i = tag_i² is satisfiable for **every** value of tag_i (tagSq_i is a private intermediate
  signal). It restricts nothing about the tag. The relation therefore says: "the prover knows a member of the tree
  with root `root`, **and this proof is for the context vector (tag_0 … tag_{k−2})**". A proof generated for one tag
  vector does not verify for another (checked by the per-index perturbation controls, `17-…`).
- The constraint is the minimal uniform way to make each tag a constrained relation input rather than an unused
  ("dummy") public signal. It adds exactly one R1CS constraint per tag (r1cs non-linear constraints 2,970 + (k − 1))
  and two PLONK gates per tag (one public-input gate + one multiplication gate; 34,077 + 2(k − 1)).
- Binding mechanisms in snarkjs, stated for completeness: Groth16 setup adds one A-polynomial row per public signal
  (`zkey_new.js`, rows nConstraints + s), PLONK adds one public-input gate per public signal. Our construct does not
  rely on these mechanisms for its meaning; it ensures every tag also enters the relation's own constraint system.
- The construct is described by this constraint only. It is not presented as the construct of any named protocol.

**Domains are constant over the grid:** Groth16 domain 2¹² and PLONK domain 2¹⁶ for every k ≤ 64, so k does not change
setup-domain-dependent verifier constants' structure. Only k changes the verifier's operation counts.

**Nesting:** instance j uses tags tag_j,0 … tag_j,k−2, the first k − 1 entries of one fixed 63-element tag vector per
instance (`14-…`). Lower-k instances are prefixes of higher-k instances.

## 3. Semantic anchors (VALIDATION; same verifier template, meaningful public inputs)

| Circuit | k | Public inputs | Constraints beyond membership |
|---|---|---|---|
| `c1_a4` | 4 | root, nullifier, scope, message | leaf = Poseidon₅(record, holderSecret); nullifier = Poseidon₂(holderSecret, scope); messageSq = message² |
| `c1_a8` | 8 | root, nullifier, scope, message, majorCode, issuerId, minIssueDate, epoch | leaf = Poseidon₇(record, holderSecret, issuerId, validUntil); nullifier as above; message²; issueDate ≥ minIssueDate (32-bit); epoch < validUntil (32-bit) |

Exact relations:
- `c1_a4`: "a member of the tree, holding holderSecret, presents for `scope` with one-time tag `nullifier`, bound to
  `message`".
- `c1_a8`: additionally "the credential's major and issuer are disclosed, it was issued no earlier than `minIssueDate`,
  and it is valid at `epoch`".

## 4. Disclosure variant (`c1_disc_k04`, VALIDATION)

A fixed 32-attribute credential, leaf = Poseidon₂(Poseidon₁₆(attr 0..15), Poseidon₁₆(attr 16..31)); the first three
attributes are public. Public: [root, attr_0, attr_1, attr_2] (k = 4).

## 5. FFLONK family (conditional)

`c1_ff_kKK` for k ∈ {1, 4, 16, 32}: the **same** sources as `c1_k01` / `c1_ctx_kKK` (same R1CS), FFLONK setup with the
power-19 ptau (`21-…`). The depth-0 family (`mini`) is used only if the d = 11 gate fails (RETAIN-REDUCED).
